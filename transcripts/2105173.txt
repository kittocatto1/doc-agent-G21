**Step 7 — Build chunk**
Split OCR'd text into small searchable pieces. Choose and justify: fixed-size (every N words), by paragraph, or semantic (split on topic change). Smaller = precise but loses context; bigger = keeps context but retrieves loosely.

**Step 9 — Build index**
Store those vectors so you can search them fast. Choose flat (exact, fine for small corpora) or approximate like HNSW/IVF (faster, needed at scale). Justify against your corpus size.

## The retrieval params, explained simply

Think of this as: **"search, check if it's good enough, and if not, search wider."** This is literally your A1 agentic feature — *"evidence-gated re-search — widen k and retry if top retrieval score is weak; abstain at k_max."*

- **`k`** — how many chunks to pull back on the *first* try. Like asking "give me the top 10 most relevant snippets."
- **`weak_threshold`** — the "good enough" bar. If the best snippet's similarity score is *below* this number, the system says "hmm, not confident" and tries again with more results.
- **`k_step`** — how many *extra* chunks to grab each time it retries. "Not confident with 10? Try 20. Still not confident? Try 30."
- **`k_max`** — the hard stop. If it's *still* not confident after reaching this many chunks, it gives up and **abstains** (says "I don't know") instead of guessing — this is what makes it "evidence-gated" rather than just always answering.

So the flow for one question is: `k=10 → check score → if weak, k=20 → check → if weak, k=30 → check → if weak, k=40 (k_max) → still weak → abstain.`

## Suggested values for your project

```yaml
retrieve: {k: 5, k_step: 5, k_max: 30, weak_threshold: 0.4, rerank: true, reranker: "cross-encoder/ms-marco-MiniLM-L6-v2"}
```

Why smaller than the template's `k: 10, k_max: 40`:
- Your NFR is **scalability — p95 ≤ 1.5s across the full ~224-issue corpus**. Every widening step costs time, so starting smaller (`k=5`) and growing gradually keeps the *common case* fast; you only pay the cost of a bigger search when the first attempt genuinely was weak.

AI: Good follow-up — let's break down what "reranking" actually does, since it's a separate step from the retrieval you just asked about.

## The simple idea
Retrieval (the `k`/embed/index stuff) is like a **fast, rough sort** — it uses your embedding vectors to quickly grab the top-k *roughly* relevant chunks from potentially tens of thousands of chunks. It's built for speed, not precision.

**Reranking is a second, slower, more careful look** at just those k chunks — it re-reads the actual question and each candidate chunk *together*, and re-scores them for "does this chunk actually answer this specific question," then re-sorts them. It catches cases where the fast search grabbed something that *looks* similar in vector-space but isn't actually the right answer.

## Why two steps instead of one
- **Embedding search (fast):** compares the question's vector to each chunk's vector *independently* — this is why it can scale to your whole ~224-issue corpus in milliseconds and hit your scalability NFR.
- **Reranker (slow but accurate):** looks at the question *and* chunk *side by side* in one pass — much more accurate, but too slow to run on thousands of chunks. So you only run it on the small shortlist (your `k`) that embedding search already narrowed down.

Think of it like: embedding search is skimming a library's card catalog to find 10 books that *might* have your answer; the reranker is actually flipping to the right page in each of those 10 and checking which one really answers your question.

## The specific model: `cross-encoder/ms-marco-MiniLM-L6-v2`
This is a small, pretrained model trained specifically for this "question + passage → relevance score" task (MS MARCO is a well-known passage-ranking dataset). It's called a **cross-encoder** because it encodes the question and the passage *together* (crossed) rather than separately — which is exactly why it's more accurate but slower than your embedding model.

## Why this matters for your project specifically
Your agentic feature is *evidence-gated re-search* — widen k, check confidence, retry. The **reranker's score is what "confidence" actually means** in that loop. Without reranking, you'd only have the rough embedding similarity to judge "is this good enough" — with reranking, you get a much more trustworthy signal for `weak_threshold` to check against, which makes your abstain-or-answer decision more reliable.

For A2's evidence section (Section 5), this also means your "one real retrieval example" is stronger if you show: embedding search returned these 10 candidates → reranker picked *this* one as top → and it really is the correct page.

import io

def extract_page_image_direct(pdf_path, page_num, output_path):

    page = doc[page_num - 1]
    images = page.get_images(full=True)

## `layout.py` implementation

```python
"""Stage 2 — layout detection / segmentation"""
from __future__ import annotations
from PIL import Image
from ..contracts import Page, Region

# Maps the pretrained model's own label names to the 4 kinds our contract allows.
_LABEL_MAP = {
    "Text": "text",
    "Title": "heading",
    "List": "text",
    "Table": "table",
    "Figure": "figure",
}

_model = None  # lazy-loaded once, reused across all pages in this run


def _get_model(cfg: dict):
    global _model
    if _model is not None:
        return _model
    import layoutparser as lp
    score_thr = cfg.get("layout", {}).get("score_thr", 0.5)
    _model = lp.Detectron2LayoutModel(
        config_path="lp://PubLayNet/faster_rcnn_R_50_FPN_3x/config",
        extra_config=["MODEL.ROI_HEADS.SCORE_THRESH_TEST", score_thr],
        label_map={0: "Text", 1: "Title", 2: "List", 3: "Table", 4: "Figure"},
    )
    return _model


def _sort_reading_order(boxes: list[dict], page_width: int) -> list[dict]:
    """Sort boxes into multi-column reading order (E2): left column top-to-bottom,
    then next column — NOT naive top-to-bottom across the whole page, which would
    scramble BYTE's 2-3 column layout."""
    if not boxes:
        return boxes

    gap_px = 0.04 * page_width  # tolerance for "same column" grouping

    columns: list[list[dict]] = []
    for box in sorted(boxes, key=lambda b: b["bbox"][0]):
        x0 = box["bbox"][0]
        placed = False
        for col in columns:
            col_x0 = min(b["bbox"][0] for b in col)
            if abs(x0 - col_x0) <= gap_px * 3:
                col.append(box)
                placed = True
                break
        if not placed:
            columns.append([box])

    columns.sort(key=lambda col: min(b["bbox"][0] for b in col))  # left-to-right

    ordered: list[dict] = []
    for col in columns:
        col.sort(key=lambda b: b["bbox"][1])  # top-to-bottom within column
        ordered.extend(col)
    return ordered


def detect(pages: list[Page], cfg: dict) -> list[Region]:
    """Detect text/table/figure/heading regions, in correct multi-column reading order."""
    model = _get_model(cfg)
    regions: list[Region] = []

    for page in pages:
        image = Image.open(page.image_path).convert("RGB")
        layout = model.detect(image)

        boxes = []
        for block in layout:
            kind = _LABEL_MAP.get(block.type, "text")
            x0, y0, x1, y1 = map(int, block.coordinates)
            boxes.append({"bbox": (x0, y0, x1, y1), "kind": kind})

        ordered_boxes = _sort_reading_order(boxes, page_width=image.width)

        for box in ordered_boxes:
            regions.append(Region(page_id=page.id, bbox=box["bbox"], kind=box["kind"]))

    return regions
```

## The reading-order sorter — this is the important part
```python
def _sort_reading_order(boxes: list[dict], page_width: int) -> list[dict]:
```
This takes all the detected boxes on **one page** and puts them in the order a human would actually read them.

```python
    gap_px = 0.04 * page_width
```
This defines "how close together (in pixels) do two boxes need to be, horizontally, to count as being in the same column." It's calculated as a percentage of page width rather than a fixed number, so it scales correctly whether your page image is small or large.

```python
    columns: list[list[dict]] = []
    for box in sorted(boxes, key=lambda b: b["bbox"][0]):
```
`b["bbox"][0]` is the box's **left edge x-coordinate** (bbox = `(x0, y0, x1, y1)` = left, top, right, bottom). We sort all boxes left-to-right first, so we process them in a sensible order while grouping.

```python
        x0 = box["bbox"][0]
        placed = False
        for col in columns:
            col_x0 = min(b["bbox"][0] for b in col)
            if abs(x0 - col_x0) <= gap_px * 3:
                col.append(box)
                placed = True
                break
        if not placed:
            columns.append([box])
```
For each box, we check: "does its left edge line up closely with any column we've already started?" If yes, add it to that column group. If no existing column matches, start a brand new column group. This is how 3 separate text columns on a page get grouped into 3 separate lists, rather than one jumbled list.

```python
    columns.sort(key=lambda col: min(b["bbox"][0] for b in col))
```
Now sort the *columns themselves* left to right (column 1, then column 2, then column 3) — so we read them in the right order.

```python
    ordered = []
    for col in columns:
        col.sort(key=lambda b: b["bbox"][1])
        ordered.extend(col)
    return ordered
```
Within each column, sort boxes **top to bottom** (`bbox[1]` is the top y-coordinate). Then stitch all columns together in order: all of column 1 top-to-bottom, then all of column 2 top-to-bottom, etc. That final `ordered` list *is* your reading order — remember, there's no separate field for it, so list position is the only place this information lives.

## `chunk.py`

```python
"""Stage 4 — chunk text"""
from __future__ import annotations
from ..contracts import Chunk

# Simple whitespace-based token approximation. Real subword tokenizers (BPE etc.)
# would count differently, but for a first pass this keeps chunk.py dependency-free.
# NOTE this is a design choice — write it in design_choices.md, since a more precise
# option (e.g. the embedding model's own tokenizer) exists but adds a dependency here.

def _token_count(text: str) -> int:
    return len(text.split())


def split(chunks: list[Chunk], cfg: dict) -> list[Chunk]:
    """Re-chunk to cfg['index'] size/overlap.

    Input: one raw Chunk per OCR'd region (small, region-sized pieces, already in
    correct multi-column reading order from layout.py — this function must NOT
    reorder them, only regroup them).

    Output: Chunks resized to ~chunk_tokens words each, with ~overlap words of
    context repeated between consecutive chunks, never crossing a doc_id boundary.
    """
    index_cfg = cfg.get("index", {})
    target_tokens = index_cfg.get("chunk_tokens", 256)
    overlap_tokens = index_cfg.get("overlap", 32)

    # Group by doc_id first, preserving input order within each group.
    # This guarantees we never merge text from two different issues together,
    # and never scramble the reading order layout.py already established.
    by_doc: dict[str, list[Chunk]] = {}
    for c in chunks:
        by_doc.setdefault(c.doc_id, []).append(c)

    output: list[Chunk] = []

    for doc_id, doc_chunks in by_doc.items():
        buffer_words: list[str] = []
        buffer_page_ids: list[str] = []
        chunk_idx = 0

        def flush():
            nonlocal chunk_idx
            if not buffer_words:
                return
            text = " ".join(buffer_words)
            # de-duplicate page_ids while preserving order
            seen = set()
            ordered_pages = [p for p in buffer_page_ids if not (p in seen or seen.add(p))]
            output.append(Chunk(
                id=f"{doc_id}_c{chunk_idx:04d}",
                doc_id=doc_id,
                text=text,
                page_ids=ordered_pages,
            ))
            chunk_idx += 1

        for c in doc_chunks:
            words = c.text.split()
            for w in words:
                buffer_words.append(w)
                if c.page_ids:
                    buffer_page_ids.extend(c.page_ids)

                if len(buffer_words) >= target_tokens:
                    flush()
                    # start next chunk with the last `overlap_tokens` words carried over,
                    # so context isn't lost right at a chunk boundary
                    carry = buffer_words[-overlap_tokens:] if overlap_tokens > 0 else []
                    carry_pages = buffer_page_ids[-1:] if buffer_page_ids else []
                    buffer_words = list(carry)
                    buffer_page_ids = list(carry_pages)

        flush()  # final partial chunk for this doc, if any words remain

    return output
```

## Key design decisions explained

**Grouped by `doc_id` before chunking, not chunked globally.** If we didn't do this, the tail end of one BYTE issue could get merged with the start of the next issue into one chunk — nonsensical, and would corrupt `page_ids`/citations.

**No re-sorting anywhere.** Since `Region`/`Chunk` have no `reading_order_idx` field (per our earlier finding), the *only* thing preserving reading order is never touching list order — this function only groups and merges, never sorts.

**Overlap carries words, not full chunks.** `chunk_tokens: 256, overlap: 32` means: build up to 256 words, cut, then start the *next* chunk with the last 32 words repeated — so a sentence split awkwardly at a chunk boundary still has some context on both sides. This is standard RAG chunking practice.

**Token approximation via whitespace split** — flagged clearly as a simplification. Real subword tokenizers (what your embedding model actually uses internally) count differently than raw word-count. Worth noting as a limitation in `design_choices.md`; a more precise version would tokenize with the actual Jina model's tokenizer, at the cost of adding that dependency here.

## `versioning.py`

```python
"""Data — corpus versioning (which corpus version -> which result)"""
from __future__ import annotations
import hashlib
import json
import os
from datetime import datetime, timezone


def snapshot(corpus_dir: str) -> str:
    """Hash + record a corpus version id."""
    file_records = []
    for root, _, files in os.walk(corpus_dir):
        for fname in sorted(files):
            fpath = os.path.join(root, fname)
            size = os.path.getsize(fpath)
            with open(fpath, "rb") as f:
                content_hash = hashlib.sha256(f.read()).hexdigest()[:16]
            file_records.append(f"{os.path.relpath(fpath, corpus_dir)}:{size}:{content_hash}")

    file_records.sort()
    combined = "\n".join(file_records)
    version_id = hashlib.sha256(combined.encode()).hexdigest()[:12]

    record = {
        "version_id": version_id,
        "corpus_dir": corpus_dir,
        "n_files": len(file_records),
        "created_at": datetime.now(timezone.utc).isoformat(),
    }

    os.makedirs("data/versions", exist_ok=True)
    out_path = f"data/versions/{version_id}.json"
    with open(out_path, "w") as f:
        json.dump(record, f, indent=2)

    print(f"✅ Corpus snapshot saved: {version_id} ({len(file_records)} files) → {out_path}")
    return version_id
```

```python
"""Stage 4 — chunk text"""
from __future__ import annotations
import json
from pathlib import Path
from ..contracts import Chunk

CHUNK_DIR = Path("data/interim/chunks")


def _token_count(text: str) -> int:
    return len(text.split())


def split(chunks: list[Chunk], cfg: dict) -> list[Chunk]:
    """Re-chunk raw per-region OCR chunks to cfg['index'] size/overlap.

    Input: small, region-sized Chunks from ocr.transcribe() (one per detected
    region — text/table/heading blocks), already in correct multi-column
    reading order from layout.py. This function regroups them, never reorders.
    """
    index_cfg = cfg.get("index", {})
    target_tokens = index_cfg.get("chunk_tokens", 256)
    overlap_tokens = index_cfg.get("overlap", 32)

    by_doc: dict[str, list[Chunk]] = {}
    for c in chunks:
        by_doc.setdefault(c.doc_id, []).append(c)

    output: list[Chunk] = []

    for doc_id, doc_chunks in by_doc.items():
        buffer_words: list[str] = []
        buffer_page_ids: list[str] = []
        chunk_idx = 0

        def flush():
            nonlocal chunk_idx
            if not buffer_words:
                return
            text = " ".join(buffer_words)
            seen = set()
            ordered_pages = [p for p in buffer_page_ids if not (p in seen or seen.add(p))]
            output.append(Chunk(
                id=f"{doc_id}_c{chunk_idx:04d}",
                doc_id=doc_id,
                text=text,
                page_ids=ordered_pages,
            ))
            chunk_idx += 1

        for c in doc_chunks:
            words = c.text.split()
            for w in words:
                buffer_words.append(w)
                if c.page_ids:
                    buffer_page_ids.extend(c.page_ids)

                if len(buffer_words) >= target_tokens:
                    flush()
                    carry = buffer_words[-overlap_tokens:] if overlap_tokens > 0 else []
                    carry_pages = buffer_page_ids[-1:] if buffer_page_ids else []
                    buffer_words = list(carry)
                    buffer_page_ids = list(carry_pages)

        flush()

    # Checkpoint, matching layout.py/ocr.py's pattern — lets embed.py (or you,
    # re-running this notebook later) reload without recomputing.
    CHUNK_DIR.mkdir(parents=True, exist_ok=True)
    out_path = CHUNK_DIR / "chunks.json"
    with out_path.open("w", encoding="utf-8") as f:
        json.dump([c.model_dump() for c in output], f, indent=2, ensure_ascii=False)
    print(f"Saved {len(output)} final chunks to {out_path}")

    return output
```

## `store.py`

```python
"""Stage 4 — vector store"""
from __future__ import annotations
import json
from pathlib import Path
import numpy as np
import faiss
from ..contracts import Chunk

INDEX_DIR = Path("data/index")


def build(chunks: list[Chunk], vectors: np.ndarray, cfg: dict) -> None:
    """Persist a vector index (cfg['index']['type'])."""
    index_cfg = cfg.get("index", {})
    dim = vectors.shape[1]

    # HNSW ("Hierarchical Navigable Small World") — an approximate index.
    # M = how many links each vector keeps to its neighbors in the graph.
    # Bigger M = more accurate search, slower to build, bigger file on disk.
    m = index_cfg.get("hnsw_m", 32)

    index = faiss.IndexHNSWFlat(dim, m)

    # efConstruction: how hard the graph tries to find good neighbors while
    # BUILDING the index. Higher = better quality index, slower one-time build.
    index.hnsw.efConstruction = index_cfg.get("ef_construction", 200)

    # efSearch: how hard it searches at QUERY time. This is your main lever
    # for the scalability NFR — higher efSearch = more accurate but slower
    # per query; lower = faster but risks missing the true best match.
    # Tune this against your P95 <= 1.5s target directly.
    index.hnsw.efSearch = index_cfg.get("ef_search", 64)

    vectors = np.ascontiguousarray(vectors.astype("float32"))
    index.add(vectors)

    INDEX_DIR.mkdir(parents=True, exist_ok=True)
    faiss.write_index(index, str(INDEX_DIR / "index.faiss"))

    # FAISS only stores vectors + an internal integer id (0, 1, 2...) — it
    # knows nothing about your Chunk objects. We save this side-table so
    # retriever.py can map "FAISS returned internal id 47" back to a real
    # Chunk (its text, doc_id, page_ids) for citations.
    metadata = [c.model_dump() for c in chunks]
    with open(INDEX_DIR / "chunks_meta.json", "w", encoding="utf-8") as f:
        json.dump(metadata, f, ensure_ascii=False, indent=2)

    # These are exactly the numbers your A2 Section 4 report needs.
    size_mb = (INDEX_DIR / "index.faiss").stat().st_size / (1024 ** 2)
    print(f"✅ Built HNSW index: {len(chunks)} chunks, dim={dim}, "
          f"M={m}, size={size_mb:.2f} MB → {INDEX_DIR / 'index.faiss'}")


def load(cfg: dict):
    """Load the persisted index + its chunk metadata."""
    index_path = INDEX_DIR / "index.faiss"
    meta_path = INDEX_DIR / "chunks_meta.json"

    if not index_path.exists():
        raise FileNotFoundError(f"No index found at {index_path} — run build() first.")

    index = faiss.read_index(str(index_path))

    # efSearch doesn't get saved with the index — reset it here in case
    # something changed in cfg since build() ran.
    index_cfg = cfg.get("index", {})
    index.hnsw.efSearch = index_cfg.get("ef_search", 64)

    with open(meta_path, "r", encoding="utf-8") as f:
        chunk_dicts = json.load(f)

    chunks = [Chunk(**d) for d in chunk_dicts]

    print(f"Loaded index: {index.ntotal} vectors, dim={index.d}")
    return index, chunks
```

def split(chunks: list[Chunk], cfg: dict) -> list[Chunk]:
    index_cfg = cfg.get("index", {})
    target_tokens = index_cfg.get("chunk_tokens", 256)
    overlap_tokens = index_cfg.get("overlap", 32)

    by_doc: dict[str, list[Chunk]] = {}
    for c in chunks:
        by_doc.setdefault(c.doc_id, []).append(c)

    output: list[Chunk] = []
    for doc_id, doc_chunks in by_doc.items():
        buffer_words, buffer_page_ids, chunk_idx = [], [], 0

        def flush():
            nonlocal chunk_idx
            if not buffer_words:
                return
            text = " ".join(buffer_words)
            seen = set()
            ordered_pages = [p for p in buffer_page_ids if not (p in seen or seen.add(p))]
            output.append(Chunk(id=f"{doc_id}_c{chunk_idx:04d}", doc_id=doc_id, text=text, page_ids=ordered_pages))
            chunk_idx += 1

        for c in doc_chunks:
            for w in c.text.split():
                buffer_words.append(w)
                if c.page_ids:
                    buffer_page_ids.extend(c.page_ids)
                if len(buffer_words) >= target_tokens:
                    flush()
                    carry = buffer_words[-overlap_tokens:] if overlap_tokens > 0 else []
                    carry_pages = buffer_page_ids[-1:] if buffer_page_ids else []
                    buffer_words, buffer_page_ids = list(carry), list(carry_pages)
        flush()
    return output

Me: if we use FAISS and HNSW, my question is, where the chunks will be saved if we dont use vectordb like qdrant?

AI: Good question — this is actually the single biggest conceptual difference from your Qdrant project, so worth being precise about it.

## The key fact: FAISS only ever stores vectors + a plain integer ID
When you call `index.add(vectors)`, FAISS assigns each vector an internal ID — just `0, 1, 2, 3...` in the order you added them. That's it. **FAISS has no concept of "chunk text," "doc_id," or "page_ids" — it doesn't know or care what a vector represents.** It's purely a math structure: vectors in, nearest-neighbor search out, integer IDs as the only label.

## So where does the actual chunk text live?
**In a separate file you maintain yourself** — this is exactly what `chunks_meta.json` in the `store.py` I wrote earlier is for. Two files, saved side by side:

```
data/index/
├── index.faiss          ← FAISS's own binary file: just vectors + the HNSW graph structure
└── chunks_meta.json     ← YOUR file: the actual Chunk objects (text, doc_id, page_ids...)
```

The connection between them is **position/order**: the chunk at position 0 in `chunks_meta.json` corresponds to internal FAISS ID 0, position 1 → ID 1, and so on. When you search:

```python
distances, indices = index.search(query_vector, k=5)
# indices = [[3, 47, 12, 900, 5]]  <- just integers, meaningless on their own

results = [chunks[i] for i in indices[0]]  # <-- THIS is where you translate ID -> real chunk
```
That lookup line is the entire "connection" — you're using the FAISS-returned integer as a plain Python list index into your own saved chunk list.

## Why Qdrant felt different (and easier) in your NCTB project
Qdrant is a full **database**, not just a search-math library — it stores the vector *and* whatever metadata/payload you attach to it *together*, in the same system, and it hands you back the actual record (including your original text) directly from a search call. You never had to build that ID→text mapping yourself because Qdrant did it internally.

With FAISS, you're doing manually what Qdrant did automatically: **you** are the "database," and the JSON file is your storage layer.

## Practical implication for your `retriever.py` later (A3)
Whoever builds `retriever.py` will need to `load()` *both* files together (which is exactly why `store.load()` returns `(index, chunks)` as a pair, not just the index) — the index alone is useless without its matching chunk list.

## One thing to watch on Kaggle/Colab
Both files live on the **notebook session's local disk**, which is wiped when the session ends. Before your session closes, make sure to either commit both files into the repo (if small enough), push to Google Drive, or download them — otherwise you'll have to rebuild the whole index next session, which given your OCR/embedding costs, you don't want to redo casually.

## The full picture, one sentence each
- `build()`: turn chunks+vectors into a searchable structure, save it in two matched files.
- `load()`: bring those two matched files back into memory, ready for `retriever.py` to search — where a query gets embedded, FAISS returns nearest integer IDs, and those IDs are used to look up the real chunk text from the loaded `chunks` list.

Me: Straight from `pipeline.py` — look at the actual wiring:

```python
chunks = chunk.split(text, cfg)                 # Stage 4a — YOUR chunk.py output
hooks.run(hooks.BEFORE_INDEX, {"chunks": chunks})
vectors = embed.encode(chunks, cfg)             # Stage 4b — embed.py's output
store.build(chunks, vectors, cfg)               # Stage 4c — store.py
```

## The answer: it's the exact same `chunks` list, reused twice
`chunk.split()` produces the `chunks` list once. That **same variable** gets passed into `embed.encode(chunks, cfg)` to produce `vectors` — and then that **same `chunks` variable** gets passed *again* into `store.build(chunks, vectors, cfg)`. It's not re-fetched or reloaded from anywhere — it's literally one Python list, sitting in memory, handed to two different functions in sequence.

## Why this guarantees the position-matching we talked about
Since `embed.encode()` does `texts = [c.text for c in chunks]` internally, and never reorders, filters, or shuffles that list — vector at position 0 came from `chunks[0]`, vector at position 1 came from `chunks[1]`, and so on, **only because nothing in between touched the order.** `store.build()` then saves that exact same `chunks` list (as `chunks_meta.json`) alongside those exact vectors — so the pairing is preserved purely by "nobody reordered anything along the way," not by any explicit ID-matching logic.

## Where this could quietly break — worth knowing
If `embed.py`'s `encode()` ever internally does something like sorting, deduplicating, or dropping empty-text chunks before embedding, you'd end up with **fewer vectors than chunks**, and the position-matching would silently break — vector 5 might no longer correspond to `chunks[5]`. This is exactly why in the `encode()` I wrote earlier, there's no filtering/reordering logic at all — it processes `chunks` in the exact order given, one-to-one, on purpose.
