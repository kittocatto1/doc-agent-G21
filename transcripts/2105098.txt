AI: # doc-agent — Architecture Briefing (Lead Architect View)

## 1. The Core Architecture & Seams (Mental Model)

**Fixed vs. fill-in — the basic contract:**
Think of the repo as a house with load-bearing walls already built. You furnish the rooms; you don't move the walls.

- **FIXED (never touch structurally):** `contracts.py` (data shapes — `Page`, `Region`, `Chunk`, `Query`, `Citation`, `Answer`, `ToolResult`), `hooks.py` (the seam mechanism itself), `pipeline.py` (the Stage 0–9 order), the agent loop in `agent.py`, and the tool names/signatures in `tools.py`. CI enforces this via `tests/test_structure.py`.
- **What you actually do:** fill in the marked `# IMPLEMENT` function bodies (`[fill]`), write config/tasks/reports (`[author]`), and — for cross-cutting stuff — wire your logic into a fixed attachment point (`[wire]`).
- **Where you make choices:** only in `configs/` — which model, which parameters, per stage. You never choose *where* code lives.

**Cross-cutting features (grounding, security, PII, tracing) — how they actually work:**
These aren't single files you edit once — they're behaviors that need to fire at multiple points across the whole pipeline (e.g., PII redaction has to happen wherever text could leak; logging has to happen at every step). So instead of scattering that logic everywhere, the architecture uses a **publish-subscribe pattern**:

1. **`hooks.py`** defines named **seams** — fixed checkpoints in the pipeline/agent loop (e.g., `BEFORE_ANSWER`, `ON_STEP`, `ON_TOOL_CALL`, `AFTER_ANSWER`).
2. Each feature (e.g., `llm/postprocess.py` for grounding, `governance/pii.py` for redaction, `logging_conf.py` for tracing) owns its logic and calls `register(seam, handler)` to attach itself to a seam.
3. **`wiring.py` → `register_all(cfg)`** is the *single manifest* that actually turns all these registrations on — one place to audit "what's wired where."
4. At runtime, `hooks.run(seam, ctx)` fires every handler registered at that seam, in order, threading context through.

So: **owner module has the logic, `hooks.py` defines when it runs, `wiring.py` is the master switch-list.** `docs/cross-cutting.md` documents the full owner→touchpoint map.

**The "Strict No-File-Creation" rule:**
Every deliverable — every Python module, notebook, script, report, config, test — **already exists as a named stub in the starter repo.** Your job across all four milestones is to *edit those stubs*, never create new files. This applies uniformly: from `src/doc_agent/*` implementation files down to `reports/final_report.md` and even the optional-feature backlog (E1–E39) — each enhancement has a pre-assigned home file. If you're creating a new file, you're off-spec.

## Now let's write `get_data.sh`

Here's the script, built around everything we've established:
- Your 14-issue subset (1975–1993 spread, including the 3 issues already referenced in your `tasks.jsonl`)
- Downloads only the PDF per issue (via `ia download --glob`)
- Writes into `data/raw/` (which now transparently lands on `/mnt/projects`)
- Structured so extending to the full 176 later is a small change, not a rewrite

```bash
#!/usr/bin/env bash

# A1 — fetch or recreate your scanned corpus into data/raw/

set -euo pipefail

RAW_DIR="data/raw"
mkdir -p "$RAW_DIR"

# Subset for A2 (14 issues, 1975-1993). Extend this array toward the
# full 176-issue byte-magazine-YYYY-MM set for later milestones.
ISSUES=(
  "byte-magazine-1975-09"
  "byte-magazine-1978-07"
  "byte-magazine-1980-07"
  "byte-magazine-1981-05"
  "byte-magazine-1982-04"
  "byte-magazine-1983-11"
  "byte-magazine-1983-12"
  "byte-magazine-1984-01"
  "byte-magazine-1985-06"
  "byte-magazine-1986-08"
  "byte-magazine-1987-09"
  "byte-magazine-1988-05"
  "byte-magazine-1989-04"
  "byte-magazine-1992-03"
  "byte-magazine-1993-06"
)

echo "Fetching ${#ISSUES[@]} BYTE issues into $RAW_DIR ..."

for id in "${ISSUES[@]}"; do

done

echo "Done. Contents of $RAW_DIR:"

```
