# Per-stage design choices (A2 deliverable). Fill every cell.

| Stage | Problem statement | Data | Model | Methods | Design | Development | Deployment | MLOps |
|---|---|---|---|---|---|---|---|---|
| 0 Frame | Answer grounded questions about scanned BYTE Magazine issues for a retro-computing researcher/enthusiast, citing the source page | Public-domain BYTE Magazine scans (Internet Archive), multi-column layout as our data speciality | N/A (framing stage) | RAG over an agentic pipeline | Scalability is our primary NFR (p95 <=1.5s/query) -- constrains every downstream choice | Framing decisions (domain, speciality, NFR) were fixed in A1 and carried forward unchanged into A2, per the Grounding Gate requirement that these stay identical across milestones | manifest.yaml declares the three axes and points to the corpus -- this file itself is the deployable, checkable record of our framing decisions, not a served component | manifest.yaml functions as the version-anchor for the whole project's axes; any change to domain/speciality/NFR is a change to this one file |
| 1 Ingest+Enhance | Load raw PDF pages into a consistent Page schema | 15 BYTE issues, 6,603 pages, ~7% dimension variance | N/A -- no enhancement model used | fitz/PyMuPDF rendering; enhancement not implemented (enabled: false) | Enhancement skipped to preserve latency budget under our NFR | Verified via eda.ipynb: page counts and dimensions cross-checked against expectations (300-page floor, 60k-word floor) before trusting downstream stages built on this output | Page objects are ephemeral, in-memory outputs consumed directly by the layout stage -- no standalone persisted artifact at this stage, unlike layout/OCR which checkpoint to disk | Corpus-level hashing (versioning.py) covers the raw files this stage reads, giving traceability even though ingest itself has no separate checkpoint |
| 2 Layout | Detect and classify regions in multi-column reading order | Same corpus; ~7% dimension variance | DocLayout-YOLO, DocStructBench checkpoint | Zero-shot detection + _sort_reading_order() column-grouping by x-coordinate | Directly serves our multi-column data speciality -- column-aware ordering is the core mechanism | Tested on individual held-out pages first (e.g. byte-magazine-1988-05_p110: 38 regions detected, cleanly split into two x-coordinate clusters matching the corpus's two-column layout) before running across full issues | Detected regions are persisted per-document to data/interim/regions/<doc_id>.json via _save_regions(), consumed by the OCR stage; not committed to Git (gitignored interim data) | Per-document region JSON acts as a lightweight cache -- reruns can reuse saved regions without re-running detection, useful given DocLayout-YOLO inference cost |
| 3 OCR | Transcribe text from each detected region, respecting region type | Held-out labels: 15 hand-transcribed pages; 11/15 issues OCR'd, 4 remaining | Qwen2-VL-2B-Instruct | Zero-shot, region-kind-specific prompts, checkpointed every 25 regions | VLM chosen for region-type-aware prompting a traditional OCR engine can't do | Tested on single pages before scaling to Kaggle; validated with real word-level F1 against held-out labels (0.856 on 1981-05_p132; 0.193 on 1983-12_p019, traced to a page-indexing offset in that document, not a genuine OCR failure) | transcribe() checkpoints incrementally to data/interim/ocr/chunks.json and resumes on restart, skipping regions already OCR'd -- built specifically because Kaggle sessions can die mid-run | The checkpoint-and-resume mechanism is itself an MLOps decision: it converts an unreliable, long-running Kaggle job into a restartable one without losing completed work, which mattered in practice when we had to recover 2 truncated OCR output files mid-session |
| 4 Index | Group OCR'd regions into retrievable chunks, embed, and index -- incrementally as more issues finish OCR | ~256-word chunks, 32-word overlap, grouped by doc_id, reading order preserved; corpus entirely English | BAAI/bge-small-en-v1.5 (384-dim); FAISS HNSW (m=32, ef_construction=200, ef_search=64) | store.py's build() appends new-issue vectors to the existing index rather than rebuilding from scratch; duplicate doc_id detection prevents accidental re-indexing | Switched from Jina to BGE-small-en-v1.5: limited GPU time made Jina's 0.6B unnecessary, and its multilingual support is wasted on an all-English corpus | Tested the knowledge-base stages incrementally: layout and reading order on individual pages, then OCR outputs, then chunking/embedding/FAISS indexing on a small subset before processing all valid OCR files on Kaggle. Fits the large corpus because full-corpus experimentation is expensive -- small tests catch issues (incorrect project paths, malformed OCR JSON, embedding dimension mismatches, missing FAISS dependencies, duplicate issue insertion) before committing to the complete dataset. Cost: small samples may not expose every failure mode present across the full corpus. Local run of the complete pipeline was still finishing dependency setup as of submission | FAISS HNSW index persisted as index.faiss with chunks_meta.json; loaded via store.load(); treated as a data artifact, not source code, not committed to Git. Fits the large corpus: the index regenerates from the pipeline rather than being stored in the repo; incremental updates let newly OCR'd issues be added without rebuilding. Cost: the index must be regenerated or transferred when deploying to a new environment -- a dedicated artifact/data-versioning system would help at production scale | data/versioning.py -- SHA256-hashes the corpus directory, records a version id + file count + timestamp per snapshot. Fits reproducibility ("which corpus version produced this result"); costs a small amount of hashing time; would move to DVC if we needed branching/rollback across many corpus versions |
| 5 Retrieval | Find the most relevant chunks quickly enough to meet our latency NFR | Indexed chunks from Row 4 | cross-encoder/ms-marco-MiniLM-L6-v2 reranker | retrieve (k=10) -> widen if weak (k_step=10, k_max=40, weak_threshold=0.35) -> rerank -> abstain | Evidence-gated re-search balances recall against p95 <=1.5s; this is the required agentic behaviour (widen-then-abstain), not optional | Not yet built; planned test: unit-test the widen-then-abstain logic on questions we know are answerable vs. genuinely out-of-corpus, before wiring into the full agent loop | Not a separately deployed component -- retrieval runs in-process as part of the served agent (Row 8); no standalone deployment artifact for this stage alone | Planned: log recall@k per query once live, to catch regressions as the index grows across A3/A4 |
| 6 Agent | Decide step-by-step, know when to abstain | Same indexed corpus | LLM controller (model not yet pinned in config.yaml) using the 9 fixed tools | max_steps=8; autonomy="act-with-approval"; budget_usd=0.05/query | Bounded step count and per-query budget directly enforce predictability under our scalability NFR -- an unbounded agent risks both cost and latency blowups | Not yet built; planned test order: verifiable (exact-match) questions first since they're cheap to grade automatically, judged/subjective questions second | Not a separately deployed component -- the agent loop runs inside the same served process as retrieval (Row 8) | Planned: extend the checkpoint/resume pattern already proven in OCR (Row 3) to log every tool call and step count per query, making runaway or abstention behaviour auditable |
| 7 RL/RLVR | Optional bonus: improve extraction via checkable reward | Verifiable question set (exact-match gold) | PPO (rl: {algo: "ppo", train_policy: false}) | Reward = +1 on exact quote match | Not yet attempted (train_policy: false); genuinely bonus-tier work, deliberately lowest priority against our core NFR-driven build | Will only be attempted if core A3 deliverables (agent, evaluation) are solid with time remaining -- will not risk core marks chasing bonus RL | Same as Retrieval/Agent -- no standalone deployment artifact; a trained policy, if produced, would simply replace the untrained controller in Row 6 | Planned: if attempted, log reward per training step so before/after accuracy claims are backed by a real curve, not a single before/after number |
| 8 Serving | Make the agent reachable by a real user over the internet | N/A | serve: {batch: true} | Docker container + API + UI, matching the required serving-stack pattern | Batching chosen specifically to help meet p95 <=1.5s at higher query volume -- serving one-by-one leaves latency more exposed to per-request overhead | Not yet built; planned: load-test the served endpoint with concurrent requests to verify the latency target holds under realistic traffic, not just single-query dev testing | Hugging Face Spaces (deploy: {target: "hf-spaces"}) -- free, simple hosting matching the course walkthrough's own suggested default; container = program + API + UI | Planned: monitor error rate, abstention rate, and latency once live, per A4's required monitoring signals |
| 9 Eval | Measure correctness, groundedness, abstention behavior | Task suite: verifiable + judged + out-of-corpus questions (to be authored in A3) | LLM-judge for non-checkable questions (specific judge model not yet chosen) | eval/metrics.py stubs: recall_at_k, groundedness, citation_accuracy, ece, subgroup_gap; only ocr_f1() implemented and tested so far | Metric selection maps directly to what A3 grades: recall@k for retrieval, groundedness/citation_accuracy for the no-hallucination requirement, ece for calibration | Planned: implement remaining metrics the same way ocr_f1() was -- synthetic known-input tests (identical/no-overlap/partial-match cases) before running against real pipeline output | Not a served component -- evaluation runs offline against pipeline output, not as part of the live agent | Planned: re-run the full metric suite from a fresh clone with pinned seeds before A3 submission, to confirm reproducibility claims are real, not assumed |
